## 為什麼大多數 AI 沒想到這個解法？

### 1. **思維慣性：燈箱就該用 `contain`**
幾乎所有燈箱元件（Lightbox、Magnific Popup、Fancybox 等）預設都用 `object-fit: contain` 或 `background-size: contain`，因為目標是「完整顯示整張圖片」。AI 訓練資料裡 99% 的燈箱範例都是這樣寫的，所以自然會沿用這個「標準答案」。
### 2. **過度工程化 (Over-engineering)**
遇到「移動圖片焦點」這個需求時，多數開發者（和 AI）會本能地想：
＞ 「需要移動圖片位置 → 用 `transform: translateY()`」
＞ 「需要放大縮小 → 用 `scale()`」
＞ 「需要限制移動範圍 → 加邊界檢測」

結果就是一套複雜的 JS 矩陣運算，還容易出 bug。

### 3. **對 CSS `object-*` 家族的認知不足**
`object-fit` 和 `object-position` 其實是 2015 年就有的 CSS 標準，但很多人（包括 AI）對它們的印象停留在「用來控制 `＜img＞` 或 `＜video＞` 在容器裡怎麼塞」，很少想到「可以直接用 `object-position` 做焦點移動」。

### 4. **「顯示完整內容」的迷思**
設計師和開發者通常認為「燈箱就是要把整張圖完整顯示給使用者」，所以自然選擇 `contain`。但 11ce.htm 的場景不同——網格裡已經看過縮圖了，燈箱是為了**細節瀏覽**，所以 `cover` 裁切反而更合理，而且可以順便解決黑邊問題。

```css

.item img, .item video {
  object-fit: cover;
  object-position: 50% var(--obj-pos-y);
}
```

## 具體問題分析

### 1. DOM 節點持續累積
```javascript
// 目前寫法：只加不減
function renderBatch(start, count) {
  // ... 永遠 append 新節點
  gal.appendChild(frag);
}
```
**問題**：滾動 1000 張圖片後，DOM 有 1000 個 `.item` 節點。瀏覽器要維護所有節點的佈局、樣式、事件監聽，記憶體持續上升。

**解法**：實現 DOM 回收（RecyclerView 模式），只保留視口前後 N 個節點。

### 2. 圖片記憶體未釋放
```javascript
// 離開視口的圖片，img 元素仍在 DOM 中，src 仍佔用記憶體
```
**問題**：瀏覽器不會自動釋放不可見圖片的解碼緩衝區。

**解法**：滾出視口一定距離後，設置 `img.src = ''` 或 `img.removeAttribute('src')`。

### 3. 影片資源未釋放
```javascript
// 影片 pause 後，記憶體仍被佔用
if (item.type === 'video') {
  el.pause();
  // 缺少：el.src = ''; el.load();
}
```
**解法**：影片滾出視口後，清空 `src` 並呼叫 `load()`。
